# 後戻りしにくい設計判断は、フィーリングで即決しない

外から見える名前・構成 (バイナリ名、サブコマンド名、フラグ名、環境変数の prefix、
package/module path、ディレクトリ構成、設定ファイルの形式など) は、いったん採用
されると使用箇所がコード全体・ドキュメント・外部の参照に散らばり、後から変える
コストが、最初に決めるコストよりずっと高い。`goro` というバイナリ名を十分検討せ
ずに決めた結果、module path (`github.com/nananek/goronation`) との不一致が後か
ら問題になり、`goro` → `goronation` への 91 ファイル・940 箇所に及ぶリネームが
必要になった (2026-09)。

## 対象を見分ける

次のどれかに当てはまれば「後戻りしにくい判断」として、下の手順に従う。

- 名前が、コード内部の識別子にとどまらず、利用者が直接打つ文字列 (コマンド名・
  フラグ・環境変数名) や、外部に公開される文字列 (module path・リポジトリ名・
  CLI の出力・ファイル形式) になる。
- 採用後、複数ファイル・複数 package にまたがって同じ文字列が繰り返し出現す
  ると予想される (1 か所の変更では済まなそうか)。
- 一度公開・リリースすると、利用者側の互換性を壊さずには変えられない。

当てはまらない、ローカルな変数名・内部関数名・実装の都合による一時的な選択は
対象外 (通常の裁量で決めてよい)。

## 手順

1. その場のフィーリングで 1 案に決め打ちしない。候補を複数、理由つきで挙げる。
2. 「後から変えるコストがどれくらいか」を一言で見積もる (影響しそうなファイル
   数の目安、外部公開の有無)。
3. 利用者に確認してから決める。確認なしに進めるのは、上の「対象を見分ける」
   に当てはまらないと判断した場合だけ。
4. 決めた理由を、その場のやり取りだけに残さない。このリポジトリでは、決定と
   その理由の正は ADR (`docs/adr/`、ADR 0003)。対象が特定の package に閉じる
   なら、その package の `doc.go` にも書く (doc-durability-check と同じ理由:
   その場のやり取りは、プロジェクトの記録ではない)。

## 踏んだ実例 (同じ形を疑う)

- `goro` というバイナリ名を、十分検討せずに決めた。module path が
  `github.com/nananek/goronation` (リポジトリ名) であるにもかかわらず、
  バイナリ名だけ別の短い名前で先に決めてしまい、後から不一致が問題になって
  `goro` → `goronation` のリネームが必要になった。91 ファイル・940 箇所に及ぶ
  変更になった。
