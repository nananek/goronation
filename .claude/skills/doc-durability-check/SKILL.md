# その場のやり取りは、プロジェクトの記録ではない

複数のエージェント (レビュー担当・実装担当など) が、その場で情報をやり取りする経路 (チャット・共有のメモ・一時的な文書の受け渡しなど、道具は何であれ) は、**プロジェクトの一部ではない**。そこは、やり取りが終われば残らない前提で扱う。**あとに残す必要がある内容は、プロジェクト自身の記録 (commit・PR の説明やコメント・バージョン管理下の doc や ADR) に書いて、はじめて残る**。

## レビュー担当への指示

- レビューの報告やパッチを、その場のやり取りの経路に置いても、それだけでは仕事は終わっていない。**パッチは、実装担当が commit してはじめて残る。報告 (散文) は、実装担当が PR の説明に書き写してはじめて残る**。
- それが起きたことを、自分の締めの報告で確かめずに「レビュー完了」と報告しない。確かめる方法: 対象の PR を見て、自分が見つけた問題・直した内容が、commit の一覧か PR の説明に、要点として (参照先の名前だけでなく) 出ているかを見る。
- 出ていなければ、締めの報告で、実装担当 (か、依頼した側) に、その旨を明記する。「その場のやり取りに置いた」だけを完了の根拠にしない。

## 実装担当への指示

- レビューの報告・パッチを受け取ったら、パッチを commit で取り込む。**それに加えて、PR の説明にも要点 (レビューした対象・見つかった問題の中身・直した commit) を追記してから**、レビューの依頼や merge の準備に進む。
- PR の説明に「詳細は、その場のやり取りの記録を参照」とだけ書いて済ませない。その参照は、やり取りが終われば辿れなくなる。
- 要点は要約でよい (やり取りの全文を貼らない)。問題の中身・再現の要旨・直した commit の対応があれば足りる。

## 複数 PR にまたがる計画

- ある計画 (複数 PR に分けて進める進め方など) を、複数のエージェント・複数の PR で使い回すときも、同じ規則。**それを使う最初の PR の説明・commit メッセージ・doc や ADR に、要点を残す**。その場のやり取りの記録だけを頼りに、後続の PR を進めない。
- 計画そのものが決定 (設計・進め方) を含むなら、「事実の正は 1 か所」の方針 (このリポジトリでは ADR 0003) に従い、行き先 (ADR・Issue・doc.go) に落とす。その場のやり取りは、そこに落ちるまでの下書きの置き場として扱う。

## この skill 自身への注意

この skill は、エージェントへの指示 (プロンプトの攻撃面)。権限を与える・チェックを省く・レビューなしの merge を促す文言は書かない。書くのは、手順と確認のしかただけ。
