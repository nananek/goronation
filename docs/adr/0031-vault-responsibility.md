# 0031. Vault は保管と署名だけを持ち、egress は使うたびに Vault から引く (M2)

- 状態: 採用
- 日付: 2026-09-30
- 関連: [Issue #1](https://github.com/nananek/goronation/issues/1) (I2・「Vault (Passkey PRF)」・未決)、ADR 0032・0033・0034・0036

## 状況

Issue #1 は、Vault を「秘密の唯一の保管先」とし、GPG 署名・egress への注入用の lookup・エージェントのログイン状態の保管と復元だけを持つと書く。ただし、Vault と egress の境界 (egress が資格情報を保持するのか、使うたびに問うのか) は、未決だった。いまの資格情報は、ホストの平文のファイル (`credfile`、0600) に置いてある。

## 決定

1. **Vault は、次の 3 つだけを持つ。** (a) 資格情報 (トークン・API キー。名前で引く) の保管、(b) GPG の秘密鍵での署名、(c) エージェントのログイン状態の保管と復元。これ以外 (鍵・PRF 出力・保管した値の一括の取り出し) は、実装しない。
2. **egress は、資格情報を保持しない。** 注入する要求ごとに、`credential.Source` (ADR 0032) で Vault から引き、その要求の間だけ使う (いまの `egress/gateway` も、要求ごとに `Token` を呼ぶ)。Vault が施錠中 (未解錠) なら、引けず、注入しない。要求は通さない (fail closed)。
3. **値を受け取ってよいのは、ホストのデーモンだけ。** 檻には、値を渡さない (I2)。例外は、ログイン状態を、同じエージェントの檻の作成時に、復元することだけ (ADR 0032)。
4. **Vault 自身は、外部のプログラムを起動しない** (I1)。署名は Vault が持つ鍵で行うが、gpg を動かす檻の形 (入力は署名対象と固定の引数だけ・ネットワーク無し・shim が UDS で要求) は、M5 の別の ADR で決める。
5. **既存の `credfile` は、Vault の実装ができるまで残す。** 置き換えは、`credential.Source` の実装の差し替えで行う (呼び手は変えない)。

## 帰結

- 施錠中は、push・PR・API の注入が止まる。デーモンの再起動のたびに、解錠 (ADR 0033・0035) が要る。
- egress が値を持たないので、施錠が、次の要求からすぐに効く。egress の側に、値の写しが残らない。
- 要求ごとに復号するため、Vault の読み出しが、要求の経路に入る。メモリ上の復号なので、遅延は小さい。

## 代替案

- egress が、解錠時に値を受け取って持つ: 施錠しても、egress のメモリに残る。値のある場所が増える。
- egress が、値を期限つきでキャッシュする: 施錠の効きが遅れる。期限の設計も要る。
- Vault が注入まで行う: 責務が混ざり、Vault が通信の経路に入る (egress の許可リスト・ポリシーと重なる)。
