# 0025. chat の耐久イベントログの失敗は、縮退して知らせる (M2)

- 状態: 採用 (2026-10-01 に追記: 完了条件 8 のロックは、専用の `events.lock`。ADR 0023)
- 日付: 2026-09-30
- 関連: [Issue #1](https://github.com/nananek/goronation/issues/1)、ADR 0011・0023・0024・0026・0027

## 状況

- ADR 0023 の DB は、書き込みの error・ディスクの枯渇・ロックの待ちの超過・破損・上限で、失敗しうる。DB はセッションごとで、書くのはその serve だけなので、他のセッションの処理では失敗しない。
- ログは履歴の可用性のためで、承認の関門ではない。承認の状態は `Conversation` が持つ (ADR 0011)。
- Issue #1 に、この項目専用の完了条件が無かった。

## 決定

1. **ログの失敗は、エージェントの出力の読み取りと配信を止めず、エージェントを殺さない。** その起動は以後書かず、リングだけで動く (M1.5 と同じ)。
2. **黙って縮退しない。** `hello.durable=false` と、serve の標準エラー出力で知らせる (`--no-event-log` のときも `durable=false`)。
3. ログの状態は承認に影響しない。承認の状態は DB に依存しない。
4. 開くときの失敗 (壊れている・版が違う) は、自分のファイルを作り直し、それも失敗すれば縮退する。
5. 縮退の条件 (書き込みの error・キューの溢れ・リングの押し出しに間に合わない・1 回のコミットが 5 秒超・50 ms 超の連続) と、書き込みの構成は、ADR 0027。

### 完了条件 (SSE 耐久化。ADR 0023・0024・この ADR)

1. リングを溢れる出力のあとでも、`after=N` の再接続で、durable のイベントが欠けず・重複せず (省略の印なしに) 続く。
2. DB・リング・ライブの境目に、取りこぼしも重複も無い。
3. ログの失敗・上限で、エージェントの出力の読み取りは止まらず、縮退が hello で分かる。
4. ディスクの使用量に、起動あたりと全セッションの合計の上限がある。
5. `generation` の不一致・不正な `after` は、全再送に倒れる。
6. `--no-event-log` で、ディスクに何も書かれない。
7. 未決の権限要求は、`after` と保持の範囲に依らず、再接続で届く (ADR 0024 決定 3)。
8. **正常終了では、DB ファイルが残らない。異常終了の残りは、次の serve の起動で破棄される (それまで残る)。** 破棄は、`events.lock` が取れる (持ち主が死んでいる) ものだけ (ADR 0023 決定 5)。
9. 書き込みの尾・`Hub` の Mutex の保持・WAL を含むディスクの使用量は、ADR 0027 の完了条件を満たす。

## 帰結

- ディスクの不具合が、進行中の作業を中断させない。代わりに、その間の履歴は、リングを溢れると失われる。

## 代替案

- **書き込みの失敗で serve・エージェントを止める (fail closed)**: ログは関門ではない。止めると、ディスクの不具合が、進行中の作業の中断になる。
- **黙って縮退する**: 履歴が残っていると誤解した利用者が、再読み込みで欠けに気づく。通知する。
