# 0033. Vault の鍵は、passkey の PRF から作るラップ鍵で、本体鍵を包む (M2)

- 状態: 採用
- 日付: 2026-09-30
- 関連: [Issue #1](https://github.com/nananek/goronation/issues/1) (「Vault (Passkey PRF)」)、ADR 0031・0034・0035

## 状況

Vault は、passkey の WebAuthn PRF 拡張の出力で封じる。「iPhone で解除して Linux で使う」ので、PRF 出力は、ブラウザからデーモンに届く。passkey は複数登録でき、1 つでも運用できる。ccserver では、クライアントが申告した PRF 値で、既存のラップが置き換わる不具合があった (PR 190)。

## 決定

1. **3 段の鍵にする。** PRF 出力 (32 バイト) → **ラップ鍵** (passkey ごと) → **本体鍵** (Vault に 1 つ・32 バイトの乱数)。本体鍵が、保管する全項目を暗号化する。本体鍵は、初期化のときに `crypto/rand` で作り、平文では、メモリの外に出さない。
2. **ラップ鍵は、HKDF-SHA256 で作る。** 入力は PRF 出力、salt は Vault の ID (初期化で作る 16 バイトの乱数)、info は用途の固定の文字列と credential ID。本体鍵は、ラップ鍵で AEAD (AES-256-GCM) 暗号化し、passkey ごとに 1 つ保存する (AAD は Vault の ID と credential ID)。
3. **項目は、本体鍵から HKDF で作る項目ごとの鍵で、AEAD 暗号化する。** AAD は、Vault の ID・種類 (資格情報・署名鍵・ログイン状態)・名前・形式の版。別の項目・別の Vault の暗号文は、復号できない。
4. **ラップは、追加だけ。** 既存の credential のラップを、置き換える・消す経路を作らない。ラップの集合を変える処理は、`addWrap` の 1 か所に集める。追加できるのは、(a) 解錠済みで (本体鍵がメモリにある)、(b) 既に解錠できる passkey と、追加する passkey の 2 回の認証が、同じ儀式で済み、(c) その credential ID のラップが無いときだけ。
5. **クライアントが申告した PRF 値は、復号を試す入力にだけ使う。** 失敗しても、Vault の保存内容は変わらない。偽の PRF 値を送っても、ラップが変わらないことを、回帰テストで固定する。
6. **PRF に渡す入力 (salt) は、Vault の ID から作る固定値にする。ローテーションしない。** PRF 出力は、ログにも監査の記録にも残さない。使い終えたら、メモリから消す (`clear`)。
7. **一度漏れた PRF 出力は、自動では失効しない。** 対処は reset だけ (ADR 0034)。
8. **暗号は、標準ライブラリだけ** (`crypto/hkdf`・`crypto/aes`・`crypto/cipher`・`crypto/rand`)。外部の module は、足さない。

## 帰結

- passkey の追加・削除で、本体鍵と保管した内容は、作り直さない (ラップが増えるだけ)。passkey を 1 つ失っても、残りで解錠できる。ただし、失った passkey の PRF が漏れていれば、reset まで、それで復号できる。
- 追加に 2 回の認証が要るので、乗っ取られたセッションだけでは、攻撃者の passkey を足せない。
- ラップの ID・暗号文は、ディスクに残る。PRF 出力が無ければ復号できない (AEAD)。
- 解錠の有効期間・施錠の契機 (無操作の時間など) は、別の決定にする。

## 代替案

- PRF 出力から、直接、項目の鍵を作る: passkey ごとに、全項目を暗号化し直す。追加のたびに全項目の書き換えが要る。
- salt を回して失効する: 全 passkey の再評価が要り、漏れた PRF が、古いファイルの写しを復号できる点も、変わらない。
- 本体鍵を、ディスクに平文で置く: Vault の意味が無い。
