# 0023. chat の耐久イベントログ: 起動単位のファイル・`after=seq` の再接続 (M2)

- 状態: 採用
- 日付: 2026-09-30
- 関連: [Issue #1](https://github.com/nananek/goronation/issues/1) (M2「SSE 配信の耐久化」)、ADR 0008・0009・0013・0015、`cmd/internal/chat` の doc

## 状況

- M1.5 の `Hub` は、メモリ上のバイト上限つきリング (既定 4 MiB) だけで、永続化が無い (ADR 0009 決定 1)。溢れた履歴は失われ、繋ぎ直しは毎回全部を再送し、溢れた分は「省略」としか示せない。
- ADR 0008 の本設計は、`seq` とイベントストアを goronation が持ち、再接続は `after=seq`、再送は durable のイベントだけ、と決めている。M2 で M1.5 の簡易版をこれに置き換える (ADR 0009 の帰結)。Issue #1 に、この項目専用の完了条件は無かったので、下の「完了条件」を、この ADR で決める。
- 檻のエージェントは serve の子で、serve が死ねば檻も死ぬ。同じ起動の間は serve のメモリが生きている。したがって耐久化の実益は、(a) リングを溢れた履歴を、再接続・新規接続で失わないこと、(b) 起動後も残る記録、(c) 未決の権限要求の保持が、リングとの競合 (pin) だけに依らないこと、である。
- 現状の `seq` は起動ごとに 0 から (`Feed`)、`generation` は起動ごとのランダム値で、起動をまたぐ承認の誤適用を断つ (ADR 0013 決定 4)。UI は、既に `seq <= lastSeq` の重複捨てと `first_seq > lastSeq + 1` の省略検出を持つ (ADR 0015)。
- イベントの JSON は `Raw` を持たないが、tool の入出力・エージェントの本文 (ファイルの内容・秘密が混ざりうる) を含む。これまでメモリにしか無かったものが、ディスクに残ることになる。

## 決定

1. **耐久の単位は起動 (generation) 単位。** `seq` は今のとおり起動ごとに 0 から。serve の再起動は新しい世代で、新しいログになる。世代をまたぐ `seq` の継続・過去の起動の再表示は、この ADR の範囲外 (ADR 0013 の世代の意味を保つ。過去のログのファイルは残るので、後から足せる)。
2. **保存するのは durable のイベントだけ** (ADR 0008)。durable でないイベント (現状は `agent.frame`。将来の部分メッセージ) は、リングにだけ置き、`after` では再送しない。欠番は異常ではない。
3. **ファイル**: `<state>/groups/default/sessions/<id>/events/<generation>/NNNNNNNN.log` (ディレクトリ 0700・ファイル 0600)。**檻に bind しない場所** (chat.sock・agent・homekey と同じ階層。エージェントが履歴を偽造・消去できない)。形式は追記専用の NDJSON で、**1 行 = `Event.JSON` そのもの**。セグメント (既定 4 MiB) に分け、ファイル名は先頭の `seq`。開く・作る・読むは `hostfs` を通し (symlink・非通常ファイルを拒否)、`O_NOFOLLOW`・`O_EXCL` を使う。書き込みは 1 回の Publish のバッチにつき write 1 回で、fsync はセグメントの切り替えと Close だけ (serve が死ねば檻も死ぬので、1 件ごとの耐久性は要らない)。
4. **読み取りは敵対入力として扱う。** 1 行の上限は `DefaultMaxEvent`。`seq` の単調増加を検証し、壊れた行 (末尾の書きかけ) はそこで打ち切る。panic しない。
5. **量の上限** (既定。フラグで変えられる): 起動あたり **64 MiB**・セグメント **4 MiB**。超えたら古いセグメントから捨てる (最初の `seq` が進み、UI は既存の省略検出で「古い分は省略」を出す)。過去の起動のログは、serve の起動時に、**最新 8 起動または 7 日** を超えた分を消す。上限・GC は、エージェントの出力の読み取りを止めない。
6. **Hub**: `HubConfig.Store` (インターフェース。nil なら M1.5 と同じ挙動) を足し、`Publish`/`Update` は、リングと購読者に加えて durable を Store に追記する (write-through)。`chat` package は I/O を持たない規則を保つので、インターフェースは `chat` に、ファイルの実装は別 package (`cmd/internal/eventlog`) に置き、境界の型は基本型 (`seq`・JSON のバイト列) にする。**`Subscribe()` は変えず、`SubscribeAfter(after)` を足す**: 同じ Mutex の中で Store の終端・リングの先頭・購読者の登録を同時に取り、Store から (after, リングの先頭) の durable をロックの外で読み、リング、ライブの順に続ける。境目に取りこぼしも重複も無い (Hub の不変条件)。`Conversation` の `Publish`/`Update`/`pin` の意味は変えない。
7. **`GET /events?after=N&generation=G`** (web 経由の `/s/{id}/events` も同じ。web が値を検証して渡す): `generation` が現在の世代と一致し、`after` が 10 進数の非負整数 (2^53 未満) のときだけ、`seq > N` の durable から再送する。**一致しない・欠ける・不正な値は、エラーにせず、今までどおり全部 (pinned + 直近) を送る**。`after` が保持している最初の `seq` より前なら、保持している分から送り、hello の `first_seq` が示す (UI の既存の省略検出が働く)。`after` 付きの再接続では、pinned の前置きは送らない (`seq <= after` は既に届いていて、解決は後続の `permission.resolved` で届く)。
8. **SSE**: 各イベントに `id: <seq>` の行を足す (標準の `Last-Event-ID` ヘッダも、クエリより弱い扱いで受ける)。`id:` の値は 10 進数だけ。web の中継 (`readSSEEvents`) が許す行に `id: ` を足すが、関門は緩めない (値が 10 進数以外なら止める)。`hello` に `resumed` (`after` が効いたか)・`durable` (ストアが生きているか。縮退なら false) を足す。UI は未知の欄を無視する。UI の変更は、再接続の URL に `lastSeq` と世代を付けることと、`resumed` のとき省略の印を出さないことだけに、数行に抑える。
9. **縮退**: ストアの失敗 (書き込みの error・ENOSPC・ディレクトリの消失) は、エージェントの出力の読み取り・配信を止めず、殺さない。以後は書かず、リングだけで動き (M1.5 と同じ)、`hello.durable=false` と serve の標準エラー出力で知らせる。**黙って縮退しない。** ストアは履歴の可用性であって、承認の関門ではない。承認の状態は `Conversation` が持ち、ストアに依存しない。
10. **無効化**: `goronation serve --chat` は既定でログを書く。**`--no-event-log`** で書かない (縮退と同じ、リングだけの動作。`hello.durable=false`)。量の既定値の変更は `--event-log-max-bytes` (起動あたり) のように、フラグで行う (名前は実装の PR で確定し、この ADR に追記する)。
11. **遅い購読者**: Store から Backlog を読んでいる間にライブのキューが溢れると、今までどおり外される。外された側は進んだ `after` で繋ぎ直すので、1 回ごとに前進する。

### 完了条件

1. リングを溢れる出力のあとでも、`after=N` の再接続で、durable のイベントが欠けず・重複せず (省略の印なしに) 続く。
2. Snapshot・Backlog・リング・ライブの境目に、取りこぼしも重複も無い。
3. ストアの失敗・上限で、エージェントの出力の読み取りは止まらず、縮退が hello で分かる。
4. ディスクの使用量に上限がある。
5. `generation` の不一致・不正な `after` は、全再送に倒れる (エラーにも、別の起動の履歴にも繋がらない)。
6. `--no-event-log` で、ディスクに何も書かれない。

## 帰結

- 得るもの: リングを超える履歴の保持、`after` による差分だけの再接続、起動後に残る記録、pin だけに頼らない履歴。
- **セキュリティ上のトレードオフ (明記): tool の入出力・エージェントの本文が、ホストのディスクに、暗号化なし・0600 で残る。** ファイルの内容や秘密が混ざりうる。これまでメモリだけだったので、これは新しい露出である。既定はオンにし (履歴の欠けのほうが、日常の使い勝手を損なうため)、`--no-event-log` で書かせない選択を残す。ホストの、同じ利用者の権限で動くほかのプロセス・バックアップ・ディスクの取り出しから、読まれうる。暗号化は Vault (M2 の別項目) の後の検討で、ここでは行わない。上限と GC で、残る量と期間は限る (64 MiB・最新 8 起動または 7 日)。
- 新しい攻撃面: (a) エージェントの出力から作るファイルの読み書き (パス・名前は serve が決め、内容は 1 行ずつ検証して読む)、(b) ディスクの枯渇 (量の上限)、(c) `after`・`generation`・`id:` の注入 (web と serve の両方で厳格に検証)、(d) `after` の連打で Backlog を読ませ続ける DoS (SSE の接続の枠の中で、読む速度を上限にする)。
- `spec/v0` に語彙が増える (別の PR) と、新しい型の `durable` の付け方が、再送の範囲を決める。その ADR のレビューで、型ごとに durable の理由を確かめる。
- ADR 0009 決定 1 (「耐久ストアと `after=seq` は M2」・メモリのリング) と ADR 0013 決定 2 (SSE は「バッファ全部」を送る) は、この ADR の実装が入った時点で、この ADR に従う。`after` を持たない接続は、今までどおり動く。

## 代替案

- **セッション通し (`seq` を起動をまたいで継続)**: 世代の意味 (起動をまたぐ承認の誤適用の防止・ADR 0013) を作り直し、起動をまたぐ未決の権限要求の扱い、UI の表示の作り直しが要る。範囲が大きく増えるので見送る。
- **SQLite などの組み込みデータベース**: 依存ゼロの方針 (ADR 0004・0005 の例外の考え方) に反する。追記のみ・順に読むだけなので、ファイルで足りる。
- **1 件ごとの fsync**: serve が死ねば檻も死ぬので、得るものが無く、Publish (エージェントの出力の読み取り) を遅くする。
- **全イベント (非 durable を含む) の保存**: ADR 0008 の「再送は durable のみ」に反し、部分メッセージなどでファイルが膨らむ。
- **既定でオフ**: 履歴の欠け (溢れた分は省略) がそのまま残り、M2 の項目の目的を満たさない。既定オン + 無効化のフラグにした。
- **ログの暗号化**: 鍵の置き場所が Vault (M2 の別項目) の設計に依存する。ここでは行わず、限界として書く。
- **書き込みの失敗で serve・エージェントを止める (fail closed)**: ストアは履歴の可用性で、承認の関門ではない。止めると、ディスクの不具合が、進行中の作業の中断になる。縮退して知らせる。
- **フラグの名前**: `--no-event-log` に対し、`--ephemeral`・`--no-history` は、何を止めるか (ディスクへの記録だけ。ライブの配信は続く) が伝わらないので却下。
