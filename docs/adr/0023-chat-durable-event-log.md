# 0023. chat の耐久イベントログ: セッションごとの SQLite に、進行中の起動の durable だけを残す (M2)

- 状態: 採用 (2026-10-01 に追記: 決定 5 のロックは、当初は専用の `events.lock` だったが、**セッションのディレクトリ自身の flock に変えた (2026-10-01・attack-review L-2。lock ファイルの rename・差し替えで、生きている DB を掃除に消させられたため。vault の `lockDir` と同じ設計)**・決定 3 の固定は Hub が実際に固定した分だけ・帰結の「残る内容」を増やした。責務の分担は ADR 0053)
- 日付: 2026-09-30
- 関連: [Issue #1](https://github.com/nananek/goronation/issues/1) (M2「SSE 配信の耐久化」)、ADR 0008・0009・0024〜0027

## 状況

- M1.5 の `Hub` は、メモリ上のバイト上限つきリング (既定 4 MiB) だけで、溢れた履歴は失われる (ADR 0009 決定 1)。ADR 0008 は、イベントストアを goronation が持ち、再送は durable のイベントだけ、と決めている。
- 檻のエージェントは serve の子で、serve が死ねば檻も死ぬ。耐久化の実益は、リングを溢れた履歴を、同じ起動の間の再接続で失わないことである。
- 自前のセグメントファイルは、ローテーション・上限・GC・読み取りとの競合を、自分で実装することになる。SQLite なら、追記は INSERT、読み取りは SELECT、GC は DELETE で表せる (依存の追加は ADR 0026)。DB を全セッションで 1 つにすると、他のセッションの書き込み・終了の処理と競合する (実測: INSERT の p99 が約 130 ms・最大 252 ms で、BUSY の失敗もあった)。
- イベントの JSON は `Raw` を持たないが、tool の入出力・エージェントの本文 (秘密が混ざりうる) を含む。

## 決定

1. **耐久の単位は起動 (generation) 単位。** `seq` は起動ごとに 0 から。世代をまたぐ継続・過去の起動の再表示は範囲外。
2. **保存するのは durable のイベントだけ** (ADR 0008)。durable でないもの (現状は `agent.frame`) はリングにだけ置く。
3. **テーブル 1 つ**: `events(generation, seq, payload, pinned, created_at)`。主キーは `(generation, seq)`。`payload` は `Event.JSON` そのもの。**`pinned` は、Hub のメモリの固定 (未決の権限要求・form。ここが正) の写し** (Hub が上限 `MaxPinned` で拒否した固定は、書かない)で、GC の除外と再接続の取り出しのためだけに使う。追記は 1 回の `Update` につき 1 トランザクション (固定・固定の解除も同じトランザクションで行う)。SQL の値は、すべてバインド変数で渡す。
4. **DB ファイルはセッションごとに 1 つ**: `<state>/groups/default/sessions/<id>/events.db` (chat.sock と同じ階層)。**檻に bind しない場所**。`os.Root` の中で、通常のファイル・自分の uid・0600 を確かめて作る (0700 のディレクトリ)。書くのは、そのセッションの serve だけ。WAL モードで、`-wal`・`-shm` は DB と同じ 0600 で作られる (実測。実装 PR のテストで固定する)。`busy_timeout` は 50 ms、`synchronous=NORMAL`、`secure_delete=ON`、自動チェックポイントは既定のまま。書き込みの構成と量の上限は ADR 0027。スキーマの版 (`user_version`) が違う・壊れているときは、**自分のファイルだけを**捨てて作り直す (データは使い捨て)。
5. **保持するのは進行中の起動のログだけ。** 正常終了 (serve の終了時) に、DB ファイル (`-wal`・`-shm` を含む) を削除する。起動の始まりに、自分のセッションの前の DB ファイルを削除して、作り直す。**異常終了 (SIGKILL・OOM・電源断) の残りは、serve の起動のたびに掃除する** (**セッションのディレクトリのロックを先に取り、そのあとで `events.db` を作る**。掃除と起動が競合しても、生きている DB を消さない): `<state>/groups/default/sessions/*/` のうち `events.db` があるものについて、**そのセッションのディレクトリ自身 (DB と同じディレクトリの fd)** への `flock(LOCK_EX|LOCK_NB)` (lock ファイルは作らない。ファイルでなくディレクトリの inode に掛けるので、rename・削除・差し替えで外せない。serve が生きている間は持ち、カーネルが、死で解く。**serve の `lockDir` (`--socket` のディレクトリ) は使わない**: `--socket` で別のディレクトリになり、掃除が生きている DB のロックを取れてしまう。同じディレクトリを別の fd で取ると、自分自身とも競合する) を取り、**取れれば持ち主は死んでいるので、ロックを持ったまま DB ファイルを削除する。取れなければ生きているので、触らない。** PID での判定は、再利用で誤るので使わない。読む機能が無い今、終了した起動のログは、露出が増えるだけで使い道が無い。読む機能の PR で、保持を広げる。
6. **既定でオン。`goronation serve --chat --no-event-log` で書かない** (リングだけの動作)。量の変更のフラグ名は、実装の PR で確定し、ここに追記する。
7. 実装は `cmd/internal/eventlog` (別 package)。`chat` は I/O を持たない規則を保つので、境界のインターフェースは `chat` に置き、型は基本型 (`seq`・JSON のバイト列) にする。

## 帰結

- **セキュリティ上のトレードオフ: tool の入出力・エージェントの本文・人間の form の回答・承認の対象 (コマンド・path) が、ホストのディスクに、暗号化なし・0600 で残る。** これまでメモリだけだった露出が新しく増える。同じ利用者の権限で動くほかのプロセス・バックアップ・ディスクの取り出しから、読まれうる。既定はオンにし (履歴の欠けを防ぐという、この項目の目的のため)、`--no-event-log` で書かせない選択を残す。残るのは進行中の起動の分だけで、終了時に DB ファイルを削除する (削除はブロックを消さない。`secure_delete` は、上限による DB の中の削除にだけ効く。SSD・バックアップにも効かない)。暗号化は Vault (M2 の別項目) の後に検討する。
- 消せる決定: セグメント・ファイルの上限・ローテーション・自前の GC と、それに伴う読み取りとの競合 (読む側は WAL のスナップショットで読む)。セッションごとの DB で、他のセッションとの書き込みの競合・終了の処理の干渉が無い。作り直しも自分のファイルだけに閉じ、他のセッションの履歴を消さない。
- **限界: serve が、その後、一度も起動されなければ、異常終了の残りは残る** (掃除は serve の起動で行う)。
- 新しい攻撃面: SQLite (ADR 0026) と、DB の破損・ディスクの枯渇 (上限と縮退)。

## 代替案

- **自前のセグメントファイル (旧案)**: ローテーション・GC・上限・読み戻しの検証を、自前で持つ。SQL で足りるものを、自分で書くことになる。
- **全セッションで 1 つの DB**: 書き込み・終了時の checkpoint の競合で、INSERT が数百 ms 止まり、BUSY で失敗した (状況の実測)。`Hub` の Mutex の中で書くので、出力の読み取りが止まる。
- **過去の起動のログを残す**: 読む機能が無い今、露出が増えるだけ。
- **セッション通し (`seq` を継続)**: 世代の意味 (ADR 0013) を作り直す。範囲が大きい。
- **既定でオフ**: 履歴の欠けがそのまま残り、目的を満たさない。
- **ログの暗号化**: 鍵の置き場所が Vault の設計に依存する。
