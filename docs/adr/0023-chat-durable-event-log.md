# 0023. chat の耐久イベントログ: SQLite の 1 テーブルに、進行中の起動の durable だけを残す (M2)

- 状態: 採用
- 日付: 2026-09-30
- 関連: [Issue #1](https://github.com/nananek/goronation/issues/1) (M2「SSE 配信の耐久化」)、ADR 0008・0009・0024・0025・0026

## 状況

- M1.5 の `Hub` は、メモリ上のバイト上限つきリング (既定 4 MiB) だけで、溢れた履歴は失われる (ADR 0009 決定 1)。ADR 0008 は、イベントストアを goronation が持ち、再送は durable のイベントだけ、と決めている。
- 檻のエージェントは serve の子で、serve が死ねば檻も死ぬ。耐久化の実益は、リングを溢れた履歴を、同じ起動の間の再接続で失わないことである。
- 自前のセグメントファイルは、ローテーション・上限・GC・読み取りとの競合を、自分で実装することになる。SQLite なら、追記は INSERT、読み取りは SELECT、GC は DELETE で表せる (依存の追加は ADR 0026)。
- イベントの JSON は `Raw` を持たないが、tool の入出力・エージェントの本文 (秘密が混ざりうる) を含む。

## 決定

1. **耐久の単位は起動 (generation) 単位。** `seq` は起動ごとに 0 から。世代をまたぐ継続・過去の起動の再表示は範囲外。
2. **保存するのは durable のイベントだけ** (ADR 0008)。durable でないもの (現状は `agent.frame`) はリングにだけ置く。
3. **テーブル 1 つ**: `events(session_id, generation, seq, payload, pinned, created_at)`。主キーは `(session_id, generation, seq)`。`payload` は `Event.JSON` そのもの。`pinned` は、未決の権限要求 (Hub の固定と同じ)。追記は 1 回の `Update` につき 1 トランザクション (固定・固定の解除も同じトランザクションで行う)。SQL の値は、すべてバインド変数で渡す。
4. **DB ファイル**: `<state>/groups/default/events.db` (全セッションで 1 つ)。**檻に bind しない場所**。`os.Root` の中で、通常のファイル・自分の uid・0600 を確かめて作る (0700 のディレクトリ)。WAL モードで、`-wal`・`-shm` は DB と同じ 0600 で作られる (実測。実装 PR のテストで固定する)。`busy_timeout` は短く (既定 250 ms)。`synchronous=NORMAL`。`secure_delete=ON`。スキーマの版 (`user_version`) が違う・壊れているときは、捨てて作り直す (データは使い捨て)。
5. **保持するのは進行中の起動の行だけ。** 起動の始まりに、自分のセッションの、別の世代の行を `DELETE` する。終了時 (serve の終了時) に、自分の行を `DELETE` して `wal_checkpoint(TRUNCATE)` する。異常終了した別のセッションの残りは、そのセッションの serve が生きていないことを確かめて破棄する (判定は実装 PR で確定。候補は ADR 0013 のソケットのロック)。読む機能が無い今、終了した起動のログは、露出が増えるだけで使い道が無い。読む機能の PR で、保持を広げる。
6. **量の上限** (既定。フラグで変えられる): 起動あたり **64 MiB**、DB 全体で **256 MiB**。超えたら、書く側が自分の古い行から `DELETE ... WHERE pinned=0` で削る (最初の `seq` が進み、UI の既存の省略検出が働く)。**`pinned=1` の行は、GC の対象にしない。** それでも合計が上限を超えるなら、その起動の書き込みは縮退する (ADR 0025)。他のセッションの行は消さない。合計の大きさは `SUM(length(payload))` で数え、自分の分は、メモリの計数で持つ。
7. **既定でオン。`goronation serve --chat --no-event-log` で書かない** (リングだけの動作)。量の変更のフラグ名は、実装の PR で確定し、ここに追記する。
8. 実装は `cmd/internal/eventlog` (別 package)。`chat` は I/O を持たない規則を保つので、境界のインターフェースは `chat` に置き、型は基本型 (`seq`・JSON のバイト列) にする。

## 帰結

- **セキュリティ上のトレードオフ: tool の入出力・エージェントの本文が、ホストのディスクに、暗号化なし・0600 で残る。** これまでメモリだけだった露出が新しく増える。同じ利用者の権限で動くほかのプロセス・バックアップ・ディスクの取り出しから、読まれうる。既定はオンにし (履歴の欠けを防ぐという、この項目の目的のため)、`--no-event-log` で書かせない選択を残す。残るのは進行中の起動の分だけで、`secure_delete` と終了時の checkpoint で、破棄した内容が DB・WAL に残りにくくする (SSD・バックアップには効かない)。暗号化は Vault (M2 の別項目) の後に検討する。
- 消せる決定: セグメント・ファイルの上限・ローテーション・自前の GC と、それに伴う読み取りとの競合 (読む側は WAL のスナップショットで読む)。
- 新しい攻撃面: SQLite (ADR 0026) と、DB の破損・ディスクの枯渇 (上限と縮退)。

## 代替案

- **自前のセグメントファイル (旧案)**: ローテーション・GC・上限・読み戻しの検証を、自前で持つ。SQL で足りるものを、自分で書くことになる。
- **セッションごとの DB ファイル**: 合計の上限が数えにくい。1 つの DB なら `SUM` で数えられる。
- **書き込みの非同期化**: ring から溢れた分が、DB に届く前に失われうる。同期の INSERT にし、失敗は縮退させる。
- **過去の起動のログを残す**: 読む機能が無い今、露出が増えるだけ。
- **セッション通し (`seq` を継続)**: 世代の意味 (ADR 0013) を作り直す。範囲が大きい。
- **既定でオフ**: 履歴の欠けがそのまま残り、目的を満たさない。
- **ログの暗号化**: 鍵の置き場所が Vault の設計に依存する。
