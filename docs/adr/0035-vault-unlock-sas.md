# 0035. 解錠の儀式は、操作対象と確認コードを両方の画面に出す。経路は S9 の後に決める (M2)

- 状態: 提案
- 日付: 2026-09-30
- 関連: [Issue #1](https://github.com/nananek/goronation/issues/1) (S9・「Vault (Passkey PRF)」の SAS・未決)、ADR 0033

## 状況

WebAuthn の RP ID・origin の検証は、「正しいサイトからの要求」を保証するが、「要求を出したセッションが乗っ取られていないか」は保証しない。Linux 側 (`goronation web`) のセッションを乗っ取った者が、解錠要求を出し、iPhone の持ち主に認証させるかもしれない。ブラウザの認証の画面に、goronation は文言を出せない。

## 決定

1. **解錠の儀式は、SAS (短い確認コード) を要る。** 要件を固定する。経路は、S9 の後に、この ADR を置き換える形で決める (それまで、解錠の実装は入れない)。
   - **R1**: 要求する側 (Linux の画面) と、応える側 (iPhone) の両方に、操作対象 (どのマシン・どのセッション・何のための操作か。人間が読める形) と、同じ確認コードを出す。**対象の操作は、解錠・passkey の追加・削除 (ADR 0038)・reset 後の最初のラップ。**
   - **R2**: 応える側は、確認のボタンを押すまで、`navigator.credentials.get` を呼ばない。確認は、goronation 自身の画面で行う。
   - **R3**: 認証の challenge を、その要求の ID に束縛する。ある要求への認証で、別の要求は通らない。要求は、1 回限り・短い期限で失効する。
   - **R4**: 合わない・見覚えのない要求は、その場で拒否でき、拒否は要求を失効させる。

2. **経路の候補** (どれも、要件を満たす形を、S9 で確かめる)。
   - **A: 表示の突き合わせ。** デーモンが、要求の ID と乱数からコードを導出し、両方の画面に出す。人間が、一致を目で確かめる。
   - **B: 入力式。** 応える側だけがコードを出し、要求する側で入力させる。流し見に強いが、手間が増える。
   - **C: QR。** 要求する側が要求の ID を QR で出し、iPhone で読む。
   - 運ぶ経路 (SSE・WebSocket・URL) と、コードを challenge から導出するかデーモンが配るかも、決める。

3. **S9 で確かめること。**
   - iPhone の Safari (と Chrome) が、作成時 (`prf.enabled`) と認証時 (`prf.results`) に PRF を返すか (passkey の種類・OS の版ごと)。
   - PRF 拡張なしで作った既存の passkey で、認証時に PRF が得られるか (得られなければ、登録のやり直し)。
   - 作成時・認証時の authenticatorData に、ED (拡張データ) フラグが立つか (`cmd/internal/webauthn/authdata.go` は ED を拒否するので、立つなら登録が失敗する)。
   - passkey ごとの salt で、同じ出力が繰り返し出るか。同期された passkey が別の端末でも同じ出力か。複数の passkey の出力は独立か。
   - RP ID を `tailscale serve` の名前に固定できるか。PRF 出力を、iPhone のブラウザから `web` 経由でデーモンへ送る形で完結するか。
   - R1〜R4: 2 台の画面に同じコードを出せるか。手間と時間が、認証の期限内で実用に耐えるか。画面を切り替えても状態が残るか。A〜C のどれが使えるか。

## 帰結

- 「提案」のまま、S9 の後の ADR が置き換える。鍵の階層 (ADR 0033) は、SAS と独立に作れる。

## 代替案

- SAS なしで、passkey の認証だけにする: 乗っ取られたセッションの要求を、見分けられない。
- ブラウザの認証の画面に、操作対象を出す: 文言を制御できない。
