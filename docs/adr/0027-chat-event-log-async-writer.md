# 0027. chat の耐久イベントログの書き込みは、Hub の Mutex の外の専用 goroutine で行い、量を有界にする (M2)

- 状態: 採用 (2026-10-01 に追記: 書き手 (キュー・goroutine・W・縮退) は chat 側に置き、eventlog は同期の Store にする。ADR 0053。決定 6 は、固定の行だけが残るときに止まる)
- 日付: 2026-09-30
- 関連: [Issue #1](https://github.com/nananek/goronation/issues/1)、ADR 0023・0024・0025

## 状況

- `Hub.Update` は Mutex を持ったまま、リングへの追記と購読者への配信を行う。同期の INSERT をその中に置くと、書き込みの遅さが、エージェントの出力の読み取りと `Subscribe` を止める。
- 実測 (modernc.org/sqlite v1.40.0・ext4・1 接続・1,000 件/秒・payload 2 KB・20 秒。この環境の 1 例): 既定の自動チェックポイントは、WAL が約 4 MB で有界だが、p99.9 が約 123 ms・最大約 293 ms・50 ms 超が約 0.4%。`wal_autocheckpoint=0` + 別接続の `PASSIVE` は、尾は短い (p99.9 約 0.7 ms) が、WAL が約 316 MB まで伸び続けた (payload の合計の約 8 倍)。`RESTART`・`TRUNCATE` は WAL が有界だが、書き込みが約 50 ms 止まる (約 0.5%)。
- 同期の書き込みでは、「尾が短い」と「WAL が有界」を、同時に満たせなかった。

## 決定

1. **書き込みは Hub の Mutex の外で行う。** `Update` は、durable の Event (と固定・解除) を、有界のキューに積むだけで、待たない。専用の 1 つの goroutine が、キューを取り出し、まとめて 1 トランザクションで書く (この書き手は chat 側。ADR 0053)。
2. **DB の接続は、既定の自動チェックポイントのまま** (WAL が約 4 MB で有界)。`wal_autocheckpoint=0` と別接続の `PASSIVE` は使わない。書き込みの遅さは goroutine の中に閉じ、Mutex に及ばない。
3. **書き込み済みの最大の `seq` (W) を持つ。** DB から読むのは W まで。W より後は、リングから送る。**リングから、W を超える durable の Event を押し出す (書き込みが、リングの押し出しに間に合わない) ときは、縮退する。** 境目の取りこぼし (ADR 0024 決定 4) は、この規則で起きない。
4. **キューの上限は、リングの既定 (4 MiB) と同じ。** 溢れたら縮退する。
5. **縮退の条件** (縮退の動作は ADR 0025): 書き込みの error、キューの溢れ、押し出しに間に合わない、**1 回のコミットが 1 秒を超えた (その場で縮退)**、50 ms を超えるコミットの連続 N 回 (既定 5。ベンチで確定)。`busy_timeout` (50 ms) は、ロックの待ちの上限で、I/O の時間は縛らない。
6. **量の上限** (既定。フラグで変えられる): 起動あたり **64 MiB** (`payload` の大きさの合計を、goroutine が数える)。超えたら、`DELETE ... WHERE pinned=0` で古い行から削る (最初の `seq` が進み、UI の既存の省略検出が働く)。**`pinned=1` の行は、GC の対象にしない。** 固定は Hub の上限 (`MaxPinned`・1 件は最大 `DefaultMaxEvent`) で数が決まる。**固定の行だけが残って予算を超えるときは、GC は、それ以上削らずに止まる** (無限に回らない)。
7. **全セッションの合計**は、**異常終了の掃除のあと**に、走査した DB ファイル (`-wal` を含む) の大きさの合計が **256 MiB** 以上なら、その起動は書かず縮退する。**厳密な強制ではなく、これを許容する**: 起動あたりの上限が、合計を「256 MiB + 動いている数 × 64 MiB」に有界にし、同時に起動した 2 つの serve が両方通る競合も、この範囲で許容する。

### 完了条件 (実装 PR のベンチ。1 セッション 1,000 件/秒・payload 2 KB・上限による GC の発火を含む)

1. **WAL を含めたディスクの使用量が、上限 (64 MiB + 余白) に収まる。**
2. 書き込みを 100 ms 遅らせても、`Hub.Update` の Mutex の保持時間 (p99.9・最大) が変わらない。
3. コミットの p99・p99.9・最大を記録し、1 秒を超える書き込みが 0 件。
4. キューの溢れ・押し出しに間に合わない場合に、縮退し、境目の取りこぼしが無い。
(値は環境で変わりうるので、実装 PR の結果で確定し、ここに追記する。)

## 帰結

- 書き込みの遅れの上限は、リングの大きさ。それを超えるディスクの遅れは、縮退で受ける (履歴が欠けるのでなく、耐久化が止まる)。
- goroutine が 1 つ増える。起動あたりの 64 MiB は `payload` の合計で、DB ファイル・WAL は索引・余白の分だけ大きい (走査は、ファイルの大きさで数える)。

## 代替案

- **同期の INSERT を Mutex の中で、既定の自動チェックポイント**: 約 0.4% が 50 ms 超 (最大約 293 ms) で、出力の読み取りが止まる。
- **`wal_autocheckpoint=0` + `PASSIVE`**: WAL が有界にならず、上限と完了条件 4 (ADR 0025) を破る。
- **`RESTART`・`TRUNCATE` を定期的に**: WAL は有界だが、約 0.5% の書き込みが約 50 ms 止まる。
- **キューを溢れさせず、Mutex の中で待つ**: ディスクの詰まりが、そのまま出力の読み取りの停止になる。
